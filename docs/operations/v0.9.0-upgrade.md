# Upgrade v0.8.x to v0.9.0

The UX Harmonization release requires no architecture, database schema or
configuration migration. The v0.8.0 tag-to-candidate comparison has no changes to
`models.py`, migration paths, `.env.example`, systemd units or configuration
templates. Release hardening adds a transactional check to existing account APIs.
It does not repair a pre-existing zero-administrator installation automatically.

## Before Updating

Review the [release decision](../validation/v0.9.0-release-readiness.md).
Do not deploy an unpublished tag. Use a maintenance window and your existing
database/configuration backup process; never put backups or credentials in git.
Verify at least one enabled ADMIN exists and retain a second administrator where
appropriate. Existing self-disable/self-delete prohibitions remain unchanged.

After the release is published, from a clean deployment checkout:

```bash
git fetch origin --tags
git switch main
git pull --ff-only origin main
git show v0.9.0 --no-patch
git rev-parse HEAD v0.9.0^{commit}
```

Confirm the checkout is the intended tagged release before building. If `main`
has advanced beyond the tag, select the tagged deployment through your established
deployment procedure; do not reset an existing dirty checkout or overwrite work.

## Dependencies And Build

```bash
.venv/bin/python -m pip install -r requirements.txt
npm --prefix frontend ci
npm --prefix frontend run lint
npm --prefix frontend run build
```

The v0.8.0-to-v0.9.0 history includes the existing Stanza 1.12.2 security update
and frontend lockfile dependency updates; retain the committed lockfile. Release
hardening updates Next.js to 16.3.5, sharp to 0.35.4 (libheif 1.23.2), and js-yaml
to 4.3.2. It adds no dependency or test framework. Do not reuse a pre-hardening
`node_modules` or `.next` tree; install the final lockfile and rebuild.
No model download, reindex, demo seed, new environment setting or database
migration is required for this UX upgrade. Keep local `.env` and governed
provider/policy files unchanged.

## Activate The Build

Before restarting, inspect the installed service dependency graph:

```bash
systemctl show ai-soc-api.service ai-soc-worker.service ai-soc-frontend.service \
  --property=Requires --property=PartOf --property=After
systemctl list-dependencies --reverse ai-soc-api.service
```

On the validated host, restarting the API also propagates a restart to its worker
and frontend dependents. Schedule and explicitly approve that dependent-service
interruption; do not promise an API-only restart when the installed units couple
their lifecycles. Do not alter units or ignore dependencies just to avoid this.

If this build replaces `frontend/.next` used by the production `next start`,
activate the API in the approved maintenance window, then its matching frontend:

```bash
sudo systemctl restart ai-soc-api.service
sudo systemctl restart ai-soc-frontend.service
systemctl is-active ai-soc-frontend.service ai-soc-api.service
```

The frontend restart is required because an old Next.js process can serve HTML
referencing chunks inconsistent with the newly replaced build on disk, causing
JS/CSS 404/500 failures despite an HTML 200. An isolated development or preview
build does not require restarting production. The API restart activates the new
account invariant and version metadata; it is not needed for every UI-only build.
Do not issue unrelated worker, gateway, model runtime or database restarts. Verify
any systemd-propagated worker restart is approved and has completed successfully.
Other deployment managers should perform their equivalent reviewed activation.

## Verify

The deployed public path remains Browser -> Cloudflare Access -> Cloudflare Tunnel
-> Nginx on `127.0.0.1:8088` -> Next.js on `127.0.0.1:3000`, with API proxying to
`127.0.0.1:8008`. Nginx checks use `Host: soc.varqon.net`; adapt the hostname only
for your actual deployment. Keep Access and backend authentication enabled.

1. Check API `/health`, `/openapi.json` version `0.9.0`, and service status.
2. Run `./ai-soc validate-runtime`. Investigate actual required dependency failures;
   optional Ollama absence is not a gateway-mode generation outage.
3. Use safe existing IDs with `scripts/validate_ux12_runtime.py --incident-id ID
   --case-id ID` through the repository virtualenv. It derives current asset paths
   from HTML and compares their bytes with disk through both local ingress paths.
4. Open the seven authenticated public routes and DevTools checks in the
   [final public checklist](../validation/v0.9.0-release-readiness.md#public-verification).
5. Verify governance changes in a disposable environment. Do not delete, disable
   or demote real production administrators merely to smoke-test a release.

The API serializes account mutations before reading their state. PostgreSQL uses
a short, transaction-scoped table lock and a fresh READ COMMITTED snapshot; SQLite
test environments use an immediate write transaction. Direct privileged SQL remains
an operator responsibility, not a new database constraint. See
[Deployment guide](deployment-guide.md) for installation-specific operations.

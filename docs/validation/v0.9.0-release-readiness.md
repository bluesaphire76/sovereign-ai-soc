## Last-ADMIN Protection

The authoritative users router checks that at least one `AppUser` with role
`ADMIN` and `is_active=True` remains after every account mutation. Explicit flush
precedes validation because production sessions disable autoflush. Failure returns
HTTP 409, `At least one enabled administrator must remain.`, and closing the
uncommitted session rolls back the complete mutation. No success audit is emitted.
The frontend allowlists this controlled message instead of mislabeling every 409
as a duplicate username. No backend details or traces are displayed.

Existing HTTP 400 self-disable/self-delete guards remain stricter and unchanged.
ADMIN CRUD and self-demotion remain possible with another enabled ADMIN. Inactive
admins do not satisfy the invariant. Authentication still rechecks database roles;
stale token claims cannot retain ADMIN authorization. Tests also exercise already
authenticated concurrent requests directly against the router.

PostgreSQL account writes obtain `SHARE ROW EXCLUSIVE` on `app_users` before any
account read, use READ COMMITTED snapshots, and hold the lock through commit or
rollback. This serializes writers without blocking ordinary authentication reads.
Lock acquisition has a five-second timeout and a controlled HTTP 503 retry error.
SQLite fixtures use `BEGIN IMMEDIATE`. These are existing transaction mechanisms,
not new schemas, role values or a distributed lock subsystem. See the
[PostgreSQL locking reference](https://www.postgresql.org/docs/current/explicit-locking.html)
and [SQLite transaction reference](https://www.sqlite.org/lang_transaction.html).

Privileged out-of-band SQL is outside API enforcement. The bootstrap script only
creates an enabled ADMIN and cannot remove one; a pre-existing zero-admin database
still requires controlled operator recovery. No production user was changed during
verification. PostgreSQL tests use a disposable loopback-only PostgreSQL 18.4
container and database `ux_release_fixture`, never the operational database.

### Restart Propagation

The required frontend restart after build succeeded. The user separately
authorized API restart, explicitly excluding worker/gateway restarts. The installed
systemd dependency graph unexpectedly propagated the API restart to worker and
frontend (`Requires` dependencies); no direct worker restart command was issued.
Cancellation was attempted but denied by the existing sudo policy. The user was
immediately informed and acknowledgement was requested. This is an operational
scope deviation, not an authorized standalone worker restart.

The frontend stopped accepting connections during that transaction. Its remaining
Next process required the existing 90-second stop timeout before systemd killed it
and restarted the dependent application services at 22:02:37 CEST. All affected
services recovered and route/assets/cookie/workflow checks passed again. Gateway
and model PIDs remained unchanged. The DNS normalizer one-shot job returned to its
previous inactive state. No service unit, Nginx or Cloudflare configuration was
changed. The upgrade guide now requires inspecting/approving the installed
dependency graph before promising an API-only restart.

# Grounded Analytical Assistant V3: Milestone A

## Status and Boundary

Milestone A implements the non-generative intelligence foundation in
`services/assistant/v3/`. The production request still performs exactly one
provider generation and continues to use the closed V2 grounded claim schema,
validation, deterministic fallback, and renderer. `GroundedAnswerPlanV3` and
rich analytical prose belong to Milestone B.

No Assistant write path, database migration, debug endpoint, or additional
model was introduced. The feature continues to use the existing
`AI_SOC_ASSISTANT_ENABLED` setting; a second feature flag is unnecessary
because package construction is read-only and fails safely without replacing
the V2 response path.

## Pipeline

```text
question + validated conversation references
  -> semantic intent router
  -> semantic focus router
  -> scope resolver
  -> adaptive context policy
  -> operational/reference/advisory atoms
  -> bounded cross-incident candidate discovery
  -> authoritative SQL rehydration
  -> evidence-backed relationship graph
  -> closed V3 analytical context package
  -> existing single-generation V2 answer path
```

Intent describes the requested task. Focus identifies the relevant analytical
dimensions. Scope identifies the records to consider. Context policy selects
the typed information needed for that intent and scope. They are separate
contracts and no one value is used as a proxy for the others.

## Semantic Intent

`SemanticIntentRouter` uses the shared prewarmed embedding provider and a
declarative descriptor registry. Descriptor vectors are cached. It performs no
regex, keyword, substring, question-specific, record-specific, or generative
routing. The registry covers fact lookup, explanation, summary, investigation,
comparison, cross-incident and pattern analysis, next action, handover, and
executive summary.

A bounded secondary intent is accepted only within the configured similarity
margin. Empty, low-confidence, or unavailable embedding results resolve to the
neutral `SUMMARY` behavior, never to a narrow fact lookup.

## Adaptive Context

The policy consumes intent, focus, resolved scope, available authoritative
fields, and validated conversation state. A focused fact lookup receives
identity plus the selected fact. Broad explanations receive bounded identity,
state, entity, detection, risk, priority, correlation, MITRE, timeline,
compromise-state, and case-link context when available. Investigation and
cross-incident intents opt into additional evidence, advisory, and reference
requirements.

Raw alerts, stored AI prose, and arbitrary record dictionaries are not policy
fields. Limits independently bound operational atoms, timeline atoms,
candidates, graph incidents, reference atoms, and advisory atoms.

## Typed Atoms and Authority

The closed Pydantic contracts distinguish:

- `OPERATIONAL_AUTHORITATIVE`: facts read from SQL/API records;
- `ANALYTICAL_DERIVATION`: deterministic relationships derived from
  operational evidence, but not themselves platform-recorded facts;
- `REFERENCE_KNOWLEDGE`: bounded definitions from project documentation;
- `ADVISORY_KNOWLEDGE`: playbook and semantic-memory guidance;
- `SEMANTIC_CANDIDATE`: discovery evidence that is not operational authority.

Operational atoms cover record identity, status and canonical severity, risk
normalization, priority, host/agent, user, detection, MITRE, bounded timeline,
observables, process evidence, recorded correlation, compromise-confirmation
state, and case relationships. Each atom has a stable ID and closed typed
fields plus explicit source provenance. A recorded MITRE ID/name is operational
evidence; any definition is separate reference knowledge. Missing data creates
no substitute atom.

The current authoritative incident model exposes `escalation_reason` but no
authoritative escalation boolean (`NO_AUTHORITATIVE_ESCALATION_BOOLEAN`). The
reason is represented independently and never implies an escalation state.
The closed contract reserves `FactField.ESCALATED` and an escalation-state atom
for forward compatibility, but normalization emits that atom only when an
authoritative retrieval supplies an explicit boolean. In particular, missing
reason is not `escalated=false`, present reason is not `escalated=true`, and a
text value such as `"false"` is not accepted as state.

Reference entries come from a bounded project catalogue and cannot mutate or
override operational atoms. Advisory source excerpts are bounded, retain their
source, and are marked `retrieved=true`, `used=false`; retrieval does not mean a
validated answer used the source. Historical semantic records remain advisory
or candidate data until an existing incident is rehydrated from SQL.

The initial project-curated MITRE label catalogue is intentionally small. It
can emit, for example, the reference atom `T1112 = Modify Registry` only when an
operational T1112 atom is present. An unknown technique produces no reference
atom; the model is not allowed to substitute an ungrounded definition.

## Candidate Retrieval

Cross-incident discovery runs only for comparison, cross-incident, or pattern
analysis. The current schema supports same agent/host representation, rule,
MITRE technique, correlation type, case membership, and temporal proximity.
The contracts also reserve typed signals for user, observable, event family,
and detection family when those authoritative fields become available.

Semantic historical-incident hits can add a discovery signal but their payload
is never treated as fact. Candidate incident IDs are batch-rehydrated from the
operational database; missing/deleted IDs disappear. A candidate needs a
substantial deterministic signal or a rehydrated semantic hit. Ranking is
deterministic: same case 5.0, host/agent/user/observable 4.0, rule 3.0, MITRE or
family 2.5, correlation type 1.5, temporal proximity 0.5, plus at most 2.0 from
semantic similarity. Stable incident ID breaks ties. Discovery, rehydration,
and graph sizes have independent hard bounds.

## Evidence Graph Semantics

The graph has three non-interchangeable relationship classes:

- `RECORDED_CORRELATION`: an explicit platform relationship with operational
  provenance and `OPERATIONAL_AUTHORITATIVE` authority;
- `ANALYTICAL_RELATIONSHIP`: shared authoritative evidence derived by the
  Assistant, with `ANALYTICAL_DERIVATION` authority;
- `SEMANTIC_SIMILARITY`: a semantic candidate signal with
  `SEMANTIC_CANDIDATE` authority.

Every edge requires references present in the graph evidence registry. A
recorded-correlation edge can only be built from an explicit supported link.
Shared host does not imply causality or compromise. Shared MITRE does not imply
the same actor or campaign. Multiple shared signals do not prove a common root
cause. Semantic similarity and analytical relationships never become recorded
correlation.

The package carries a closed typed relationship registry that must exactly
match the graph. An exact `relationship_id` lookup returns the class, type,
left/right incident IDs, evidence atom references, provenance, and authority;
missing references and authority mismatches fail without NLP, string matching,
or heuristic search. This is the structural contract available to the future
`GroundedAnswerPlanV3` validator.

## Conversation State

Conversation state is a process-local, in-memory, user-and-conversation scoped
store. The optional `conversation_id` request field activates it. Owner keys
are SHA-256 digests of authenticated actor identity and role. State contains
only record IDs, intent/focus values, validated atom/relationship/knowledge
references, language, and timestamps. Previous model prose is not a state
field and cannot become authority.

The store defaults to a one-hour TTL, 16 conversations per owner, and 512 total
entries. Expired states are lazily removed; explicit scoped cleanup is
available internally. Operational IDs are revalidated when state is loaded,
so deleted incident/case references are removed. The store is intentionally
non-durable; database persistence and discourse resolution can be evaluated in
a later milestone without trusting prose.

## Compatibility and Observability

The API adds optional `conversation_id` input and bounded V3 metadata fields;
existing fields and response blocks remain compatible. Prometheus records
context build duration and package count using only the low-cardinality intent
and analysis-scope dimensions. Audit metadata records bounded counts and never
stores the question, package contents, incident IDs as labels, source excerpts,
or model output.

The analytical package contains the question, response language, intent,
focus, scope, context plan, authority-separated atoms, candidates, graph,
conversation references, limits, source registry, relationship registry, and
phase timings. It is constructed before the existing one provider call, but is
not yet supplied as a replacement answer schema. This preserves the V2
source-of-truth and grounding behavior until Milestone B.

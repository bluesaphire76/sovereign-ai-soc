# v0.8 AI Execution Gateway

## Decision

`ai-soc-inference-gateway` is the single owner of generative model execution.
The API, worker, Assistant, incident and case analysis, Recommended Playbooks,
remediation intelligence, synthetic probes, and future AI features submit typed
requests through `AiExecutionClient`. They do not select or call a provider
directly.

The gateway listens only on:

```text
/run/ai-soc/inference-gateway.sock
```

The Unix socket is local to the host and inherits the `ai-soc` runtime
directory permissions. It does not add a TCP listener or an internal bearer
secret.

## Fixed Runtime

The stable runtime accepts only:

```text
AI_EXECUTION_MODE=gateway
AI_INFERENCE_PROFILE=standard
profile=standard
model=ai-soc-standard
concurrency=1
temperature=0
```

Caller contracts do not contain provider, model path, router URL, profile, or
raw llama.cpp options. The gateway forces the local llama.cpp provider,
disables provider fallback and hidden reasoning, and rejects non-standard
profile requests before transport.

The former distributed `fast`, `standard`, and `quality` selection is retired
for active platform generation. Existing aliases can remain configured for
future separately validated work, but the gateway never selects them.

## Queue

The bounded `asyncio.PriorityQueue` uses FIFO ordering within each effective
priority:

| Priority | Work |
|---:|---|
| 100 | Contextual Assistant |
| 80 | User-triggered incident or case analysis |
| 70 | User-triggered Recommended Playbooks |
| 60 | User-triggered remediation analysis |
| 30 | Incident triage required by the lifecycle |
| 10 | Background enrichment and probes |

Only one request can generate at a time. Waiting requests age by bounded
priority points to prevent starvation. Queue capacity and per-request deadlines
are enforced. A disconnected caller cancels its queued future. A running
llama.cpp request is not preempted; the next request starts only after it
finishes.

## Readiness

At startup the gateway inspects the operator-managed llama.cpp router and
warms only `standard` within the configured startup deadline. Status is
`warming`, `ready`, `failed`, or `stopped`. Requests are accepted only while
ready. The readiness monitor re-inspects the router and rewarms standard after
a router restart.

The API no longer owns model prewarm or profile reconciliation. Its Assistant
lifespan owns only local embedding prewarm and reads gateway status.

## Boundary

Approved low-level provider modules remain implementation details used by the
gateway. Production routers, feature services, and worker code must import
`services.ai_execution.client` or use an existing wrapper backed by that
client. `tests/test_ai_execution_boundary.py` enforces this rule and rejects
raw chat endpoints, provider builders, and profile load/unload calls outside
the gateway and approved low-level modules.

## Observability

The gateway exposes `/health`, `/status`, `/v1/generate`, and `/metrics` over
the Unix socket. Prometheus metrics cover queue depth and wait, duration,
active requests, request status, deadlines, grounding rejections, fallbacks,
semantic degradation, and profile switches.

`ai_execution_profile_switch_total` must remain zero during normal
single-profile operation. Logs contain safe task, priority, latency, status,
profile, model, validation, and source-count metadata. Questions, prompts,
answers, source text, vectors, reasoning, and secrets are not logged.

## Migration

This design replaces Assistant-specific model prewarm, automatic profile
selection, direct feature-to-provider calls, and concurrent uncoordinated
generation. There is no supported dual execution path in gateway mode.

# AI Assistant Part B: Global Authoritative Analytics

Part B extends the accepted V3.2 Assistant with a global SOC scope. It does not
add a second inference pipeline. Global, incident, and case requests all publish
through the V3.2 structured response, semantic proof, and atomic fallback path.

## Execution path

```text
natural-language question
  -> shared local embedding
  -> declarative semantic analytics registry
  -> closed AnalyticsQueryPlan
  -> registry validation and plan fingerprint verification
  -> authorized SQLAlchemy record scope
  -> registered filters and aggregate/result builder
  -> typed AnalyticalResultAtom and relationship graph
  -> one Qwen generation at most
  -> V3.2 proposition validation and semantic proof
  -> atomic model publication or deterministic typed fallback
```

The model never creates, validates, repairs, or executes SQL. The query plan has
no table, column, function, join expression, or free-form SQL field. Registered
definitions are the only source of executable query structure.

## Closed query IR

The IR defines closed operations for count, list, top-k, distribution, trend,
period comparison, entity comparison, recorded relationships, and semantic
similarity. A registry definition constrains the entity, measure, filters,
dimensions, joins, ordering, limit, execution strategy, authority, and result
schema. Only combinations represented by an active registry definition are
executable.

Every plan has a canonical SHA-256 fingerprint. Deserialization rejects a plan
whose fingerprint does not match its complete typed contents.

## Authority hierarchy

- SQL rows and platform-recorded correlation relationships remain
  `OPERATIONAL_AUTHORITATIVE`.
- Counts, rankings, distributions, trends, comparisons, and bounded result sets
  are `ANALYTICAL_DERIVATION`.
- Qdrant hits and semantic-similarity relationships remain
  `SEMANTIC_CANDIDATE`, including after SQL rehydration of the candidate record.
- SQL rehydration authorizes and validates a candidate record; it does not turn
  similarity into a recorded relationship.

An analytical or semantic relationship cannot prove causality, compromise,
attacker identity, campaign membership, or a shared attack. V3.2 typed guards
enforce these non-implication boundaries.

## Authorization

The analytics executor applies the typed access policy to the SQLAlchemy query
before filters, grouping, counting, ranking, trend derivation, or result
selection. SQL-backed entity identity resolution uses the same authorized scope.
Conversation result IDs are revalidated against the current access policy before
they can become a follow-up plan.

This order is invariant:

```text
authorized record scope -> registered filters -> aggregate or result set
```

Counts and trends cannot include records hidden from the current actor.

## Temporal contract

Relative periods are resolved in `Europe/Zurich` and stored as absolute,
half-open UTC windows in the query plan and analytical proof unit. Supported
closed literals include today, this week, last 24 hours, last N days, this month,
and previous month. Period comparisons derive an adjacent previous window of
equal duration. A definition that requires time fails closed when no supported
window can be resolved.

Time-dependent analytical proof units require the resolved start and end values
as typed anchors. A response with a different date range therefore fails before
publication even when its numeric value happens to match.

## Conversation state

Global follow-ups persist only validated typed state: registry definition,
operation, entity, measure, filters, resolved window, dimensions, bounded result
IDs, and plan fingerprint. Prior generated prose is never read as authority.
Valid empty result sets are distinct from missing conversation state, allowing a
follow-up count over an empty set to return zero without a fabricated record ID.

State remains keyed by the existing owner hash and conversation ID. A state
owned by another user cannot be loaded.

## Product surface

The existing `/assistant/query` API accepts the `global` scope. The `/assistant`
workspace uses the same response blocks, source attribution, technical metadata,
and read-only role boundary as contextual assistants. It waits for the complete
validated API response and does not emulate token streaming.

The global metadata records the operation, entity, registry definition, query
fingerprint, result count, and resolved UTC window for audit and troubleshooting.
